# 企业级嵌入式工程升级计划

## 1. 文档目的

本文是 `embedded-engineering-upgrade` 分支的设计基线。它把企业级升级拆成
可独立验证、可独立回退的小阶段，避免同时修改驱动、调度和控制算法。

本轮升级遵守以下约束：

- `main` 与 `develop` 只作为稳定基线，不直接开发；
- 当前裸机协作式调度继续作为默认执行模型；
- 不调整 PID、姿态解算、混控关系和电机输出参数；
- 每次只迁移一个低风险边界，再运行主机测试和双 Keil 构建；
- 新接口先与旧接口兼容，调用方稳定后再移除旧接口；
- FreeRTOS、Flash 参数持久化和日志输出后端必须分阶段启用。

### 当前实现状态

| 阶段 | 状态 | 本分支结果 |
|---|---|---|
| 设计与保护基线 | 已完成 | 分层、非目标、验收和回退策略已固定 |
| 驱动公共契约 | 已完成 | `DriverStatus/State/Health` 已由双固件编译 |
| 最小 HAL | 已完成 | 状态灯迁移到 GPIO HAL，旧 LED API 保留 |
| FreeRTOS 架构准备 | 已完成 | 任务清单和资源预算可测试，内核未启用 |
| 参数管理基础 | 已完成 | 类型、范围、revision、schema、CRC 和事务加载 |
| 结构化日志基础 | 已完成 | 16-byte 非阻塞事件环和 bounded drain |
| 测试接口 | 已完成 | Fake GPIO、7 项 Host 测试和统一质量门禁 |

“已完成”表示基础接口和自动测试完成，不表示所有现有驱动已经迁移，也不表示
FreeRTOS、Flash 持久化或日志后端已经进入飞行运行路径。

## 2. 当前架构分析

### 2.1 已具备的工程基础

`develop` 已经提供：

- 唯一的 STM32F1 CMSIS/SPL 平台代码；
- 明确的 Master/Slave 工程边界；
- 带版本、长度和 CRC 的主从通信协议；
- 主控周期任务调度和飞行安全状态机；
- 主机单元测试、项目结构校验、双 Keil 构建和 CI；
- 构建、协议、安全、维护和发布文档。

这些能力足以作为升级基线，不需要重新组织控制算法。

### 2.2 当前主要问题

| 问题 | 当前表现 | 工程风险 |
|---|---|---|
| 驱动接口不统一 | 初始化多为 `void`，命名、状态和数据读取方式不一致 | 调用方无法区分超时、未就绪和硬件故障 |
| 设备与芯片耦合 | 设备驱动直接包含 `stm32f10x.h` 并操作 SPL | 无法在电脑端替换硬件、复用或单测 |
| 目录职责混合 | `Hardware` 同时包含设备、总线、显示和控制算法 | 依赖方向不清晰，修改影响范围难判断 |
| 全局状态暴露 | CRSF、SlaveMCU 和部分传感器公开可写全局变量 | 数据所有权与并发边界不明确 |
| 调度模型固化 | 任务发布依赖定时器中断和全局 pending 数组 | 直接迁移 FreeRTOS 容易改变周期和优先级 |
| 参数入口分散 | PID 参数通过通信解析后直接写入算法 | 缺少类型、范围、版本、CRC 和持久化边界 |
| 诊断方式零散 | 计数器、LED 和串口输出没有统一事件格式 | 无法稳定追踪故障、丢包、超时和重启原因 |
| 测试替身不足 | 仅协议和安全状态机能够在主机测试 | 驱动失败、队列溢出和参数损坏难以注入 |

## 3. 目标分层

```text
Application
  飞行状态、控制编排、任务入口
        |
Services
  参数、日志、健康监控
        |
Device Drivers
  传感器、接收机、状态灯、显示
        |
HAL Interfaces
  GPIO、SPI、I2C、UART、时间、临界区
        |
BSP / Platform Adapter
  板级引脚、STM32F1 SPL、启动和中断
```

横向依赖：

```text
Execution model
  Cooperative Scheduler（当前默认）
  FreeRTOS Adapter（后续可选）

Test support
  HAL Fake / Fault Injection / Host Tests
```

依赖规则：

1. Application 不直接包含 STM32 寄存器或 SPL 头文件；
2. Device Driver 只调用 HAL 接口，不知道具体 GPIO、DMA 或芯片实例；
3. BSP 把板级资源绑定为 HAL 实例，不解释飞行业务；
4. Services 不直接驱动硬件，通过后端接口保存或输出；
5. FreeRTOS 只出现在执行模型适配层，不渗入控制算法；
6. 测试替身实现同一 HAL 契约，不使用生产代码中的条件分支模拟硬件。

## 4. 分阶段实施

### 阶段 0：设计与保护基线

实现：

- 建立本文档；
- 固定分支、非目标和依赖规则；
- 为每个阶段定义验证条件。

验收：

- 工作从 `develop` 的已验证提交分出；
- `main` 与 `develop` 不发生提交；
- 每个阶段均可通过单独 commit 回退。

### 阶段 1：驱动公共契约

分析：

- 现有驱动返回值和生命周期不统一；
- 立即重命名全部接口会制造大量无功能差异的修改。

设计：

- 增加统一 `DriverStatus`、`DriverState` 和 `DriverHealth`；
- 规定成功为零、错误原因可区分；
- 状态结构记录初始化状态、最后错误、错误次数和最后更新时间；
- 暂不批量修改现有驱动。

验收：

- 公共契约不依赖 STM32；
- 主机测试覆盖状态转换和错误计数；
- 现有固件行为不变。

### 阶段 2：最小 HAL 与低风险驱动迁移

分析：

- LED 只涉及数字输出，不参与传感器或控制计算；
- 适合作为第一条 HAL 迁移链路。

设计：

- 建立与芯片无关的 GPIO 输出接口；
- 建立 STM32F1 SPL GPIO 适配器；
- 状态灯驱动只依赖 HAL；
- 保留 `LED1_ON()` 等兼容入口，避免一次修改所有调用方；
- 使用电脑端 Fake GPIO 测试高低电平和 active-low 语义。

验收：

- LED 引脚和亮灭电平与原实现完全一致；
- HAL 和设备驱动可在电脑端编译；
- Master 固件构建为零错误零警告。

### 阶段 3：FreeRTOS 任务架构设计

分析：

- 当前四个周期任务经过验证，直接换成 FreeRTOS 会同时改变定时源、优先级、
  栈和并发模型；
- STM32F103C8 RAM 有限，不能先引入内核再测资源。

设计：

- 把任务 ID、周期、优先级、触发方式和栈预算集中为任务清单；
- 当前协作式调度器读取同一任务定义；
- 设计 FreeRTOS 映射、通知方式、互斥规则和栈监控；
- 默认构建仍使用协作式调度；
- 暂不添加 FreeRTOS 内核和启动任务。

验收：

- 当前 2/5/10/20 ms 周期不变；
- 任务清单可被主机测试；
- 文档明确 RTOS 启用前的 RAM、时序和台架门槛。

### 阶段 4：参数管理基础

分析：

- PID 调参当前是通信解析结果直接写入算法；
- 在没有范围、版本和损坏恢复前，不应直接把 Flash 参数接入飞行控制。

设计：

- 使用描述表定义 ID、类型、默认值和上下界；
- 使用调用方提供的静态存储，不使用堆；
- 支持读取、校验写入、恢复默认值和 dirty 状态；
- 定义带 magic、schema version 和 CRC32 的持久化镜像；
- 解码先完整验证、再一次性应用，防止部分更新；
- 本阶段不把 PID 参数切换到新系统。

验收：

- 越界、错误类型、未知 ID、版本不匹配和 CRC 损坏均被拒绝；
- 损坏镜像不会改变当前参数；
- 主机测试覆盖默认值、更新和序列化。

### 阶段 5：轻量结构化日志

分析：

- 高频控制路径不能使用 `printf`；
- 字符串日志占用 Flash、RAM 和串口带宽，ISR 中格式化还会扩大时延。

设计：

- 固定大小结构记录时间、级别、模块、事件和一个参数；
- 使用调用方提供的静态环形缓冲区；
- 写入非阻塞，满时丢弃新记录并增加 dropped 计数；
- 输出后端在低优先级上下文消费；
- 第一阶段仅提供基础设施，不改变现有蓝牙遥测格式。

验收：

- 无动态分配、无格式化、无硬件依赖；
- FIFO、回绕、满队列和 dropped 计数有主机测试；
- 未接入时不改变飞行时序。

### 阶段 6：测试接口

分析：

- 企业级测试需要可替换硬件和可重复故障注入；
- 仅依靠真实板卡无法在 CI 覆盖超时、I/O 错误和存储损坏。

设计：

- 建立可复用 Fake GPIO；
- 测试公开契约，不读取模块私有变量；
- 将驱动、任务清单、参数和日志测试接入根 CMake/CTest；
- 项目校验检查新增核心文件和文档；
- 后续按相同模式增加 Fake SPI/I2C/UART/NVM。

验收：

- CI 能运行所有新增测试；
- Fake 能记录调用次数、电平和注入错误；
- 双固件构建继续通过。

## 5. FreeRTOS 启用门槛

本分支可以完成 FreeRTOS 架构准备，但只有满足以下条件后才能默认启用：

1. 确定内核版本、许可证和源码管理方式；
2. 完成静态任务/队列内存预算，禁止运行期堆分配；
3. 测量每个任务最坏执行时间和栈高水位；
4. 验证优先级反转、看门狗喂狗和失联保护；
5. 在无桨台架上对比当前调度与 RTOS 调度的周期抖动；
6. 连续运行、故障注入和断电恢复测试通过；
7. 单独提交“启用 FreeRTOS”，保留一键回退到协作式调度的能力。

## 6. 提交与回退策略

每个提交只表达一个工程目的：

1. `Plan the embedded engineering upgrade`
2. `Standardize driver lifecycle reporting`
3. `Introduce a testable GPIO HAL`
4. `Define the RTOS-ready task model`
5. `Add validated parameter storage`
6. `Add non-blocking structured logging`
7. `Expand host-side test interfaces`

阶段提交必须包含相应测试；如果固件构建失败，不进入下一阶段。

## 7. 明确非目标

本轮不做：

- 修改 PID 系数、控制公式、滤波参数或姿态解算；
- 修改电机映射、PWM 频率或最小输出；
- 改变主从协议线上格式；
- 直接把全部 `Hardware` 文件移动或重命名；
- 在未测 RAM 和时序前启用 FreeRTOS；
- 在未完成掉电安全设计前把参数写入内部 Flash；
- 在 ISR 中加入字符串日志或阻塞输出。
